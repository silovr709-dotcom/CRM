## 2. Архитектура и стек

- **Фронтенд:** React 18.3 + TypeScript 5.5 + Vite 5.4, PWA (service worker `crm-v7`), hash-роутинг.
- **Сервер:** PHP (reg.ru, «Хост-0»), один файл `server/api/index.php` (~700 строк), JSON-состояние под `flock`.
- **Синхронизация:** серверный режим (PHP, общая база) + запасной Supabase-режим (локальный/демо).
- **Хранение:** localStorage (данные), IndexedDB (файлы), сервер (общая база и blob'ы).
- **Тесты:** vitest + jsdom + testing-library; 432 теста, ~130 исходных файлов.

## 3. Функциональность (по модулям)

### CRM
- Сделки, клиенты, воронка (11 этапов), доска с drag-and-drop, массовые действия, дубли клиентов, объединение карточек.
- Быстрые касания в списке/на доске, автоматический следующий шаг при смене этапа.
- Вложения на сделках и клиентах, синхронизация файлов между устройствами.
- Задачи со сроками, повторами (ежедневно/еженедельно/ежемесячно), откладывание +1/+7.
- Напоминания: о задачах, событиях графика, днях рождения, остатках, дайджест дня.

### График монтажей
- Замеры, доставки, монтажи, свободные события (отпуск, совещание, выезд) с повторами weekly/monthly.
- Проверки накладок (бригада в день монтажа, конфликт событий).
- Печать ведомостей (Visma Mebel), экспорт ICS.

### Склад
- Приходы с фабрики по ведомости (фото или PDF с текстовым слоем), OCR (tesseract.js, rus+eng).
- Готовые позиции бланка Visma Mebel, ввод только количества.
- Остатки упаковок, отчёты.

### Сотрудники и роли
- Руководитель/менеджер/монтажник; проверка роли на сервере.
- Деньги фильтруются на сервере (монтажник не видит суммы, менеджер — без расходов).
- Управление пользователями в «Данных» (создание, изменение, удаление, сброс пароля).

### Данные и версии
- Экспорт/импорт JSON и ZIP с файлами, автокопия перед опасными действиями.
- Версии базы на сервере (последние 12), восстановление (только owner).
- Размер базы с предупреждением при > 6 МБ (лимит 8 МБ).

### Офлайн (новое, PR #32)
- Полный precache сборки по манифесту Vite (crm-v7): приложение целиком работает без сети с первого запуска.
- Локальное расписание уведомлений (Notification Triggers): ближайшие напоминания ставятся в расписание устройства, срабатывают без сети и при закрытом приложении (где браузер умеет).
- Запасной канал: экспорт напоминаний на 90 дней в календарь телефона (.ics с VALARM) — работает на любом телефоне, включая iPhone.
- Честный статус в настройках: умеет ли устройство будить само, сколько запланировано.

## 4. Безопасность

### Сервер (PHP)
- ✅ Пароли: `password_hash`/`password_verify`.
- ✅ Сессии: токен 64 hex → SHA-256 на сервере, TTL 30 дней, cookie `HttpOnly`, `SameSite=Lax`, `Secure` при HTTPS.
- ✅ Троттлинг входа: 5 неудач/15 мин по IP+логину → 429.
- ✅ Роли проверяются на сервере: деньги фильтруются в `envelopeForRole`, `settings.accounts` обнуляется для не-owner.
- ✅ Лимиты: тело 8 МБ, файл 10 МБ.
- ✅ Валидация ID файлов (`validFileId`), tmp+rename при загрузке.
- ✅ `flock` на состоянии, атомарная запись.
- ✅ Конфликты версий: 409 при устаревшей базе, не затирание.
- ⚠️ CORS `Access-Control-Allow-Origin: *` — приемлемо для same-origin приложения, но при размещении на другом домене cross-origin запросы с cookie не пройдут (браузеры отклоняют `*` с credentials). Это осознанное ограничение.
- ⚠️ Нет HTTPS-редиректа в `.htaccess` (намеренно: старый набор давал HTTP 500). HTTPS включается в панели хостинга. Проверить, что в панели reg.ru включён «перенаправлять на HTTPS».

### Фронтенд
- ✅ Нет `dangerouslySetInnerHTML`, `eval`, `new Function`.
- ✅ Нет `as any`.
- ✅ Service worker не кэширует `/api/` (запросы входа/базы зависят от заголовков).
- ✅ Токен хранится в localStorage + cookie (третий канал), не в URL.
- ⚠️ Вложения до 10 МБ читаются в память (`file_get_contents('php://input')`) — при одновременных загрузках может быть нагрузка, но для одной фирмы приемлемо.

## 5. Производительность

- Главный чанк: 637 КБ (gzip ~196 КБ) — предупреждение Vite о размере.
- Причина: код-сплиттинг через `React.lazy` был откачен (63 падения UI-тестов из-за синхронного ожидания контента). Записано в PR #31.
- PDF-воркер: 1.38 МБ (lazy, грузится только при импорте ведомости).
- OCR (tesseract.js): грузится лениво, модель качается с CDN при первом использовании.
- Рекомендация: перевести UI-тесты на `findBy*`/`waitFor` и вернуть lazy-импорты для тяжёлых экранов (Отчёты, Склад, График) — снизит первоначальную загрузку.

## 8. Найденные замечания и риски

### Документация (drift)
1. `docs/HOSTING.md` упоминал HTTPS-редирект в `.htaccess` — исправлено в этом аудите (HTTPS включается в панели).
2. `crm-schedule/README.md` описывает Supabase как основной сервер, хотя теперь основной — PHP на своём домене. Supabase остаётся запасным режимом (без PHP-сервера). Рекомендация: добавить абзац про серверный режим и ссылку на `docs/HOSTING.md`.
3. `ARCHITECTURE.md` упоминает service worker `crm-v7` — актуально.

### Зависимости
4. `npm audit`: 6 уязвимостей (3 moderate, 1 high, 2 critical) — все в dev-зависимостях (vite, esbuild, tinypool, vitest). В production-бандл не попадают. Обновление требует `npm audit fix --force` (breaking). Рекомендация: обновить Vite до 6.x и Vitest до 3.x в отдельной задаче, с прогоном тестов.

### Код
5. Главный чанк 637 КБ — см. п. 5.
6. `localReminders.ts`: использует экспериментальное свойство `showTrigger` (Notification Triggers API). Стандарт не финализирован; в Safari не работает (честно отключается через `supportsLocalScheduling`). При изменении API браузерами потребуется обновление.
7. `precacheBuildAssets`: `visit(key, new Set())` вызывается для каждого ключа отдельно — `seen` сбрасывается, но `urls` общий (Set), дубли гасятся. Корректно, но неоптимально (повторный обход). Не критично.
8. `wasShownLocally` использует окно 5 секунд — возможна гонка при быстром открытии приложения сразу после срабатывания. Низкий риск.
9. Нет автоматических тестов на UI-компоненты офлайн-блока (проверяется только логика). Приемлемо.

### Инфраструктура
10. FTP-пароль известен только пользователю; CI зависит от секретов. Если секреты потеряны — деплой останавливается, но приложение продолжает работать (статика на хостинге).
11. `api/data/state.json` не затирается деплоем (exclude в workflow) — проверено.
12. Нет автоматического бэкапа базы на сервере (только версии в state.json, последние 12). Рекомендация: периодический экспорт или бэкап на уровне хостинга (reg.ru).
