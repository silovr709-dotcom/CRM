# CRM на REG.RU: автоматическая публикация

Инструкция для владельца сайта и разработчика. Workflow
[`.github/workflows/deploy-reg-ru.yml`](../../.github/workflows/deploy-reg-ru.yml)
собирает **только интерфейс CRM** из `crm-schedule/`; он не переносит общую базу
Supabase и не делает файлы вложений общими.

## До настройки

1. Выбранный адрес CRM — **https://тверь-рецепт.рф/**. В панели домен может
   отображаться как `xn----ctbjba4ddbni5b6d.xn--p1ai`. Хостинг общий с
   калькулятором, но для CRM необходим **отдельный сайт и отдельный каталог**.
   На предоставленном снимке ispmanager папки сайтов разные: для CRM указан
   `/www/xn----ctbjba4ddbni5b6d.xn--p1ai`. Путь в панели не обязательно совпадает
   с путём внутри отдельного FTP-аккаунта: нужно проверить оба.
2. Убедитесь, что DNS выбранного адреса ведёт на нужный хостинг, а HTTPS-сертификат
   действителен. Значок SSL в панели сам по себе не доказывает, что браузер
   принимает сертификат именно для этого домена.
3. Создайте на хостинге **отдельного FTP-пользователя**, доступного только к
   каталогу CRM. Не используйте пользователя с доступом к калькулятору и его данным.
   Уточните у REG.RU имя FTP-сервера и поддержку явного FTPS с корректным сертификатом
   на порту 21. Workflow специально не переходит на нешифрованный FTP автоматически.
4. Если на старом адресе есть рабочие данные, до переноса скачайте из CRM **архив
   с файлами .zip на каждом устройстве**, проверьте число отсутствующих файлов и
   сохраните архивы в защищённом месте. Не загружайте их в каталог сайта или GitHub.

## Секреты в репозитории CRM

После подтверждения каталога владелец сам добавляет значения в **GitHub → CRM →
Settings → Secrets and variables → Actions → Secrets → New repository secret**.
Пароли не нужно отправлять в чат или помещать в код.

| Имя секрета | Что указать |
|---|---|
| `CRM_FTP_SERVER` | Имя FTP-сервера из REG.RU, без `https://`, пути и порта |
| `CRM_FTP_USERNAME` | Логин отдельного FTP-пользователя CRM |
| `CRM_FTP_PASSWORD` | Пароль этого FTP-пользователя |
| `CRM_FTP_REMOTE_DIR` | Путь до каталога CRM **относительно FTP-пользователя**, со слешем в конце. Если пользователь ограничен только этим каталогом, обычно `./`; проверьте в клиенте/панели |

Секреты другого репозитория, в том числе Calculator, автоматически в CRM не
переносятся. Если используется тот же хостинг, данные для нового пользователя
всё равно нужно задать здесь отдельно.

Если `CRM_FTP_REMOTE_DIR` равен `./` или `/`, workflow дополнительно требует
переменную `CRM_FTP_ROOT_ISOLATED = true` в **Settings → Secrets and variables →
Actions → Variables**. Создавайте её только после проверки в панели REG.RU, что
этот FTP-пользователь ограничен каталогом CRM. Иначе используйте точный путь к
отдельному каталогу и не подтверждайте изоляцию.

## Пробный запуск без изменения файлов

Workflow должен сначала оказаться в основной ветке репозитория, иначе GitHub может
не показать кнопку ручного запуска. После этого:

1. Откройте **Actions → CRM — публикация на REG.RU → Run workflow**.
2. Выберите нужную ветку и оставьте **«Проверить FTP…»** включённым (`dry_run`).
3. Дождитесь успешных тестов и сборки. Сверьте настройку FTP-пользователя и
   записанное вами значение пути с отдельной папкой CRM; GitHub скрывает значения
   секретов в журнале. Проверьте, что список планируемых изменений ожидаемый.
4. Если есть сомнения в папке, пользователе или сертификате FTPS — остановитесь;
   не включайте настоящую публикацию.

Пробный запуск предназначен только для просмотра изменений: файлы хостинга он
не меняет. Проверка сертификата FTPS строгая: если соединение не прошло, проверьте
адрес FTP-сервера и сертификат у REG.RU. Не включайте обычный FTP ради обхода ошибки.

## Разрешить автоматическую публикацию

Только после успешной пробной проверки владелец создаёт в **Settings → Secrets and
variables → Actions → Variables → New repository variable** переменную:

```text
CRM_DEPLOY_ENABLED = true
```

Кроме переменной, реальная выкладка требует файла
`crm-schedule/.reg-ru-deploy-approved` в той ветке, которую собирает workflow.
Изначально этого файла нет: его можно добавить только после проверки каталога,
пробного запуска и отдельного разрешения владельца. Это защищает от случайной
выкладки при публикации самого workflow или при уже существующей переменной.

Когда выполнены **оба** условия, изменения в `crm-schedule/`, закоммиченные и
отправленные в `main` или `arena/c931d8fc-crm`, публикуются после успешных
`npm ci`, `npm test` и `npm run build`. Изменение файла только в песочнице без
`git push` публикацию не запускает. Чтобы приостановить выкладки, удалите
переменную или установите значение, отличное от `true`; можно также удалить файл
разрешения из собираемой ветки и отправить это изменение.

Это две разрешённые ветки, публикующие в один и тот же каталог: выкладывается
последний успешно завершившийся запуск. Новые ветки других сессий попадают на сайт
после объединения с `main`, если workflow не настроен иначе.

Используется отдельный файл состояния `.crm-deploy-sync-state.json`; очистка
`dangerous-clean-slate` выключена. При выкладке файлы с совпадающими именами,
например `index.html`, могут быть перезаписаны. Синхронизатор также может удалять
файлы, которые он сам загружал ранее, если они исчезли из новой сборки. Поэтому
отдельный каталог и ограниченный FTP-пользователь обязательны. Если в каталоге есть
старые файлы, сначала выясните их назначение и сохраните копию; не удаляйте наугад
служебные каталоги и файлы, например `.well-known` или `webstat`.

## После первой публикации

- Проверьте настоящий HTTPS-адрес на компьютере и телефоне.
- На тестовых данных проверьте создание сделки, сохранение после перезагрузки,
  резервную копию и восстановление.
- Изменение домена создаёт для браузера отдельное хранилище: данные с прежнего
  адреса автоматически не появятся. Общая база и вложения требуют отдельного плана
  переноса и проверки.
- До работы команды с реальными данными нужны исправления синхронизации и импорта,
  а также серверная аутентификация и разграничение прав. Локальные роли экрана и
  пароль от сайта не заменяют ограничения на стороне базы.

## Текущая общая база

На 29.10.2026 проект Supabase, адрес которого указан в CRM, найден в подключённом
аккаунте; сервисы базы и REST сообщали, что исправны. Вызов функций чтения через
SQL с новым случайным кодом вернул «база не найдена» и пустой список версий; это
не проверка реальной записи или работы из браузера. Его основной регион —
`eu-west-2` (Лондон, Великобритания), а не Россия. Сами записи клиентов при этой
проверке не просматривались. Если используется общая синхронизация, проверьте с
юристом требования к локализации и передаче персональных данных прежде, чем
использовать реальные сведения. Размещение статического сайта на REG.RU не
переносит эту базу в Россию.

Метаданные сервера показывают, что функции чтения и записи синхронизации доступны
роли `anon` и принимают общий код; в их тексте не обнаружены прямые проверки
`auth.uid` или `auth.jwt`. Локальный выбор роли не следует считать серверной
изоляцией пользователей. До командной эксплуатации требуется отдельная доработка
авторизации и прав, а не только публикация сайта.
